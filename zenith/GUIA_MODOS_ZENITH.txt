Esta guia responde directo:
1. Para que sirve cada modo de "Decompile Mode" (y cuales no son adorno).
2. Que partes del menu YA funcionan hoy y cuales son solo maqueta UI pendiente.
3. Como se usa todo esto en la vida real (ejemplos concretos).

--------------------------------------------------------------------------------
PARTE 1: LOS 6 MODOS DEL DECOMPILER ("Decompile Mode")
--------------------------------------------------------------------------------
Ninguno de los 6 modos esta de adorno: cada uno muestra una capa distinta del
mismo script compilado (bytecode Luau). Segun lo que quieras encontrar, uno es
mucho mas rapido que otro.

1) Source  [EN CONSTRUCCION - Fase 2 (CFG ya listo; falta Structurer + Lifter)]
   - Que es:
     Reconstruye codigo Luau legible (if/else, for, while, expresiones, llamadas).
   - Para que sirve en la vida real:
     Leer la logica completa de un script como lo escribio el programador
     (condiciones, formulas de dano/cooldown, validaciones, flujo general).
   - Conviene borrarlo?
     NO: es el modo principal de lectura humana.

2) Constants  [YA FUNCIONA]
   - Que es:
     Lista todas las constantes fijas del script: strings, numeros, rutas
     (GETIMPORT como game.Players, math.clamp, table.insert) y tablas literales.
   - Para que sirve en la vida real:
     ES EL MAS RAPIDO para encontrar informacion sin leer 2,000 lineas:
     - Nombres de RemoteEvents / RemoteFunctions (ej. "BuyItem", "ThrowKnife").
     - Precios, cooldowns, velocidades, multiplicadores, URLs o mensajes de UI.
     - Servicios y modulos que importa el script.
     Ejemplo real: si un script tiene 1,500 lineas y solo quieres saber como se
     llama el Remote o la carpeta que usa, cambias a Constants y lo ves en 2s.
   - Conviene borrarlo?
     NO, es utilismo incluso cuando ya exista Source.

3) Protos  [YA FUNCIONA]
   - Que es:
     Muestra el "indice" o arbol de funciones internas (closures/callbacks) que
     hay dentro del script: nombre, linea donde empieza, parametros y jerarquia
     (padre -> hijas).
   - Para que sirve en la vida real:
     Un script grande suele tener 30 o 80 funciones (#0..#79). Protos te deja
     ver el mapa completo del archivo y localizar por nombre o linea la funcion
     exacta que te interesa (ej. #14 shootGun L240, #27 onHeartbeat L410).
   - Conviene borrarlo?
     NO: es el indice para usar junto con Function.

4) Function  [YA FUNCIONA]
   - Que es:
     Muestra una SOLA funcion (elegida en Config -> Function Target por numero
     como "14" o por nombre; vacio = funcion principal #0) con sus upvalues,
     constantes y bytecode.
   - Para que sirve en la vida real:
     Cuando un script es enorme (y "Decompile Max Lines" recorta el total),
     Protos te dice "la funcion que buscas es la #14", pones 14 en Function
     Target y ves SOLO esa funcion limpia, sin ruido de las demas.
   - Conviene borrarlo?
     NO: ahorra muchisimo tiempo en scripts grandes.

5) Upvalues  [YA FUNCIONA]
   - Que es:
     Muestra las variables locales externas que cada funcion "captura" de su
     entorno (estado compartido entre funciones del mismo script, por ejemplo
     cooldowns, tablas de estado, referencias a servicios o jugadores).
   - Para que sirve en la vida real:
     Entender que variables globales/locales del modulo comparte una funcion
     con otra (por ejemplo, que tabla de configuracion o bandera booleana
     modifica un callback).
   - Conviene borrarlo?
     Depende: si buscas simplicidad extrema, puedes mantenerlo (ocupa 1 opcion
     en el selector y no estorba) porque ayuda a depurar closures.

6) Bytecode  [YA FUNCIONA]
   - Que es:
     Desensamblado completo de instrucciones de la VM de Luau (LOADK, GETIMPORT,
     CALL, FORNPREP, JUMPXEQKN, etc.) para todas las funciones del script.
   - Para que sirve en la vida real:
     - Verificar que nunca miente: incluso si Source tiene un error de
       reconstruccion o el codigo fue ofuscado, Bytecode muestra exactamente
       lo que la VM ejecuta.
     - Depurar por que una funcion hace cierto salto o llamada exacta.
   - Conviene borrarlo?
     NO: siempre conviene tener el desensamblado exacto como respaldo.

PARTE 2: ESTADO REAL DE CADA PESTANA DEL MENU (QUE FUNCIONA Y QUE ES MAQUETA)
--------------------------------------------------------------------------------
Es importante ser 100% transparente sobre que tiene codigo real detras hoy en
zenith.txt y que son botones/secciones de plantilla pendientes:

[1] Pestana "Decompiler"  ->  FUNCIONA (Fase 1 completa, Fase 2 en curso)
    - Scan Scripts, Script Class Filter, Script Search, Script List,
      Decompile Selected, Script Path, Decompile Path, Save Decompiled,
      Decompile Mode (Function, Bytecode, Constants, Upvalues, Protos):
      TODO ESTO YA FUNCIONA EN VIVO.
    - Decompile Mode = Source: pendiente terminar Paso 2 (Structurer) y
      Paso 3 (Lifter). El Paso 1 (CFG Builder) ya esta probado.

[2] Pestana "Config"  ->  FUNCIONA
    - Decompiler Config:
      * Include Core Scripts (oculta CoreGui/CorePackages por defecto)
      * Include Nil Scripts
      * Show Line Numbers, Include Constants, Include Upvalues, Strip Comments
      * Function Target, Decompile Max Lines
    - Menu / Configs / Session:
      * Menu Keybind, Opacity, Scale, Animations, Tween Speed
      * Guardar / cargar presets JSON en workspace/Zenith/Configs
      * Reset Settings, Unload Zenith

[3] Pestana "Core"  ->  PARCIALMENTE FUNCIONAL
    - Zenith Core (Refresh Services, Cleanup Connections, Modules Loaded,
      Active Connections, Uptime): YA FUNCIONA (es el kernel de Zenith).
    - Zenith Init / Zenith Signal: controles de configuracion/contadores base.

[4] Pestana "Tools"  ->  PARCIALMENTE FUNCIONAL
    - Zenith Console: YA FUNCIONA (terminal flotante con comandos help/clear/
      echo/uptime/version/unload y Copy Console).
    - Zenith Math: YA FUNCIONA (World To Screen, Prediction, Trajectory,
      Vector Calc).
    - Zenith Inspect / Zenith Create: MAQUETA UI (aun no tienen motor conectado).

[5] Pestana "Analysis"  ->  ACTUALMENTE ES SOLO MAQUETA UI
    - Zenith Spy (Remote Spy), Memory Scanner, Extractor, VM Hook, Projectiles,
      Stealer, Env Spoofer:
      Hoy tienen los botones, listas y salidas visuales dibujadas, pero TODAVIA
      NO tienen logica de hooks/escaner conectada por detras.
    - Nota sobre "Zenith Spy" (RSpy):
      En esta columna izquierda hay ~15 controles pequenos apilados. Si quieres
      que el RSpy quede bonito, comodo y usable (estilo Cobalt / SimpleSpy:
      lista de remotes capturados a la izquierda + visor de codigo generado,
      argumentos y botones Copy/Block/Ignore/Replay a la derecha), lo ideal es
      darle una pestana o vista dedicada de 2 paneles cuando lo implementemos,
      y limpiar de "Analysis" lo que no vayas a usar.

PARTE 3: COMO APLICARLO EN UN CASO REAL (FLUJO DE TRABAJO)
--------------------------------------------------------------------------------
Ejemplo practico: quieres entender como funciona el sistema de tienda o armas de
un juego hecho por ti o que estas analizando:

Paso 1 - Escanear:
  Ve a "Decompiler" y pulsa "Scan Scripts".
  (Por defecto ya filtra los CoreScripts internos de Roblox para que veas
  directo ReplicatedStorage, Players, StarterPlayer, Workspace).

Paso 2 - Filtrar rapido:
  Escribe palabras clave en "Script Search" (ej. "shop", "gun", "client",
  "controller", "remote") o filtra por ModuleScript / LocalScript.

Paso 3 - Explorar sin ahogarte:
  Selecciona un script y pulsa "Decompile Selected".
  - Cambia "Decompile Mode" a "Constants": en segundos ves todos los strings,
    numeros y nombres de Remotes que usa ese script.
  - Cambia a "Protos": ves que funciones tiene y sus nombres/lineas.
  - Si el script es largo, escribe el indice (ej. 12) en Config -> Function
    Target y cambia a "Function" para ver solo esa funcion al detalle.
  - Cuando terminemos Fase 2, cambiaras a "Source" para leerlo en Luau limpio.

Paso 4 - Guardar para analizar o comparar:
  Pulsa "Save Decompiled" y se guarda completo en la carpeta workspace de tu
  executor (Zenith/Decompiled/<nombre>.txt), sin importar el recorte visual de
  Decompile Max Lines.

--------------------------------------------------------------------------------
PARTE 4: QUE CONVIENE BORRAR Y QUE CONVIENE MANTENER
--------------------------------------------------------------------------------
MANTENER (son utiles de verdad):
- Decompiler completo (los 6 modos: Source, Function, Bytecode, Constants,
  Upvalues, Protos).
- Config (Decompiler Config + Menu + Presets + Session).
- Tools -> Console y Math (Inspect tambien sirve mucho si luego lo conectamos
  como mini-Dex para ver instancias y propiedades).
- Core -> Zenith Core (limpieza de conexiones y servicios).
- Remote Spy (pero rediseniado en formato limpio de 2 paneles, estilo Cobalt,
  en lugar de 15 controles apretados en una columna).

BORRAR O DESACTIVAR POR AHORA (hoy solo meten ruido visual):
En la pestana "Analysis", si no planeas implementar cada uno a corto plazo,
estas secciones solo ocupan espacio y confunden porque son botones sin motor:
- Zenith Extractor (es redundante con Decompiler + Console).
- Zenith Projectiles (demasiado especifico; mejor tener RSpy + Decompiler solidos).
- Zenith Stealer (los executors suelen traer saveinstance aparte si se ocupa).
- Zenith Env Spoofer / Zenith VM Hook / Memory Scanner: mantener SOLO si vas a
  construirles logica real; si no, es mejor dejar solo un buen Remote Spy +
  Memory Scanner ligero (buscar constantes/strings en getgc) y quitar el resto.
